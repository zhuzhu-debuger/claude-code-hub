## 可以复现的代码缺陷

`withRequestMemoryLifetime` 之前只在响应 EOF、读取失败或响应体取消后释放根所有者，没有连接入站请求的 `AbortSignal`：

1. 客户端在 guard 或上游响应返回前断线。
2. 代理稍后返回 `Response`，框架已不再读取该响应。
3. 响应包装流没有发生 EOF 或 cancel，根所有者一直保留。
4. 后台宽限只在根所有者结束后启动，因此 `active > 0, draining = 0` 可以永久存在。

另一个路径是底层 `reader.cancel()` 永不 settle：原先在等待取消完成后才释放根所有者，同样无法进入后台清理宽限。

旧版真实 standalone 测试中，4 条请求在上游收到后、响应头返回前断线；上游和后台任务已经结束，仍残留 `active=4, draining=0`。正常完成和读到响应后再取消的对照阶段均通过。这解释了为何之前的回归未覆盖此缺陷。

## 修复约束

- 代理入口将入站请求 `AbortSignal` 传给内存生命周期。
- 客户端断开即结束下游响应所有权，并取消迟到或无人消费的响应。
- 正在执行的 handler 和尚未完成的取消操作各自保留显式所有权，避免只为降低统计数字而提前释放仍在使用的正文。
- 卡住的后台所有者进入已有宽限及正文清理机制，不给正常请求新增硬超时或并发门禁。
- EOF、读取错误、取消和断线之间保持幂等，正常结束移除事件监听。

参照本机 `sub2api` 的客户端断线与后台引流分离思路。CCH 已有独立计费、replay 和后台任务所有者，因此复用现有生命周期机制，不移植另一套超时体系。

## 验收范围

回归必须同时验证：响应前断线、响应已返回但未消费、读流中断线、底层取消不结束、后台计费仍在处理以及正常长流。测试检查活跃生命周期、租约和后台任务回收，并保留账本完整性断言；不能靠 GC 或进程重启让检查通过。

项目固定 Node 26.12.1 下，真实生产构建配合隔离 PostgreSQL、Redis 和 mock 上游完成两周期、8 并发验证，每条入站和出站正文均为 1 MiB：49 条上游请求恰好对应 49 条账本，17 条成功、32 条取消，其中 16 条在响应头之前断线。各阶段都在 GC 前确认后台任务、请求生命周期和正文租约归零，`forcedTotal=0`。两轮早断线后的 ArrayBuffer 均为 1,652,243 字节，增量为 0。

生命周期和真实代理入口的 23 条专项测试通过，生命周期模块行覆盖率 97.43%、分支覆盖率 83.60%。独立审阅另外通过实际 GC 对照验证断线监听不会强引用已放弃的响应流，源取消、租约释放各一次，监听器归零。参见[验收说明](memory-disconnect-acceptance-2026-10-24.md)及[结构化结果](memory-disconnect-results-2026-10-24.json)。

提交前生产构建、lint、lint:fix、typecheck 均通过；全量单测在 Node 26.12.1 下为 9470 通过、13 跳过。CI 沿用 acer-server 优先、本机回退、GitHub 上传镜像的路径。本轮已分别实测 acer 正常构建及模拟 acer 不可达后的本机 smoke 构建，两份镜像导出校验均通过。

这验证了上述可复现缺陷的修复，不代表上游账号、限流或所有历史 OOM 都已解决。生产版本保持不变，新的镜像需要单独部署后才会影响线上行为。
